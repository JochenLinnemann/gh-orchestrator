# GH Orchestrator

A small, safe orchestrator that turns GitHub tasks into reviewable multi-repo pull requests.

___GitHub is the system of record. AI is the worker.___

GH Orchestrator is not an agent framework. It is an execution layer with guardrails.

## Current Implementation Status (v0)

✅ **Complete end-to-end orchestration loop:**

1. ✅ Receives GitHub `issue_comment` webhooks and validates `/ai start`
2. ✅ Validates task via quality gates (issue exists, repos listed, criteria present, no destructive operations)
3. ✅ Claims tasks atomically by updating Projects V2 fields (`AI = running`, `Status = In Progress`, `Run ID`)
4. ✅ Plans execution with per-repo branch names following `ai/<run-id>/<slug>` pattern
5. ✅ Invokes AI worker (OpenAI or mock) with bounded task context
6. ✅ Validates AI worker results (no binary files, no schema changes, reasonable delete ratios)
7. ✅ Applies AI-generated file changes to branches
8. ✅ Commits and pushes branches, creates pull requests
9. ✅ Posts summary comment to issue with PR links and testing instructions
10. ✅ Transitions task to `AI = blocked` (waiting for review)

**Worker implementation:**
- ✅ Optional OpenAI-backed worker with GPT-4 support
- ✅ Fallback to mock worker when not configured
- ✅ AI attribution in commit messages

**Ready for manual testing:** See [Manual Testing Guide](#manual-testing-for-v0-cutover) below.

## Project Overview

GH Orchestrator is a small, self-hosted service that connects GitHub Issues and Projects to AI-powered code execution in a controlled, reviewable way.

It allows teams to:
- Define work as GitHub Issues
- Track that work using GitHub Projects (Kanban)
- Trigger AI-assisted execution explicitly
- Receive changes exclusively as pull requests (one per repository)

GitHub remains the system of record for task state, intent, and approvals.  
AI is used only as an execution tool, never as a decision-maker.

The orchestrator is designed to support **multi-repository tasks from day one**, while keeping behavior deterministic, auditable, and easy to reason about.

---

## Goals

- Use GitHub as the single source of truth for tasks, state, and approvals
- Enable AI-assisted changes without bypassing code review
- Support tasks that span multiple repositories in a predictable way
- Keep execution behavior explicit, deterministic, and auditable
- Favor small, reviewable changes over large automated refactors
- Minimize operational complexity and infrastructure requirements

---

## Non-Goals

- Fully autonomous or self-directing AI agents
- Background processes that continuously poll or act without explicit triggers
- Hidden state outside of GitHub without clear justification
- Automatic merging of AI-generated changes
- Optimization for scale before real usage justifies it
- Replacing human ownership, judgment, or accountability

## Getting Started

This project is under active development.

At a high level, the intended workflow is:

1. Create a GitHub Issue describing a task, including:
   - explicit acceptance criteria
   - a list of repositories involved
2. Add the Issue to a GitHub Project (Kanban)
3. Trigger execution by commenting `/ai start` on the Issue
4. Review the pull requests generated by the orchestrator
5. Merge changes manually once approved

This repository focuses on defining **behavior, guardrails, and architecture** first.
Detailed setup and deployment instructions live in `SETUP.md`.

For system structure and trust boundaries, see `ARCHITECTURE.md`.

## Manual Testing for v0 Cutover

**Before v0 release, execute Plan 9 (end-to-end manual verification):**

1. **Setup:**
   - Configure orchestrator with real GitHub App credentials
   - Create a test organization or use personal repos
   - Set up a GitHub Project with `AI`, `Status`, `Run ID` fields

2. **Execute one complete task:**
   - Create a GitHub Issue with:
     - Clear task description
     - Acceptance criteria (explicit checklist)
     - Repos field (comma-separated: `owner/repo1, owner/repo2`)
   - Comment `/ai start` on the Issue
   - Observe:
     - Task claimed: `AI = running`, `Status = In Progress`, `Run ID` populated
     - Branch created per repo with naming pattern `ai/<run-id>/<slug>`
     - PR opened per repo with AI-generated changes
     - Issue comment posted with PR links and testing instructions
     - Task transitioned to `AI = blocked` after PR creation

3. **Validation:**
   - ✅ PRs contain non-empty, AI-generated code changes
   - ✅ Branch names follow convention
   - ✅ Commits attributed to `gh-orchestrator[bot]`
   - ✅ Issue comment includes PR links
   - ✅ No secrets leaked in comments or commits
   - ✅ Kanban state accurate

4. **Document findings:**
   - Update `ROADMAP.md` with outcomes
   - Record any gaps in `RETRO.md`
   - If gaps discovered, create ADR in `DECISIONS.md`
